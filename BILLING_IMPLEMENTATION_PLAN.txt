MONTREAL QBANK BILLING IMPLEMENTATION PLAN
Version: 1.0
Date: 2026-08-25

OBJECTIVE

Add secure subscription billing to Montreal QBank using Stripe Checkout, Stripe Billing,
the Stripe customer portal, Supabase, Next.js, Vercel, and the existing authentication
system. Preserve the invite-only beta and demo experience while billing is developed
and tested. Enable the paywall only after test-mode and production checks pass.


RECOMMENDED LAUNCH MODEL

1. Keep account creation invite-only for the first billing release.
2. Require an authenticated invited user to subscribe before entering the paid app.
3. Offer one Montreal QBank product with two recurring prices:
   - Monthly subscription in CAD
   - Annual subscription in CAD
4. Use Stripe-hosted Checkout for purchases.
5. Use the Stripe-hosted customer portal for payment methods, invoices, and
   cancellation.
6. Allow active and trialing subscriptions to use the paid app.
7. Let cancellations retain access until the paid period ends.
8. Keep demo mode free and fully isolated from both Stripe and Supabase writes.
9. Support explicit complimentary access grants for administrators, reviewers,
   and selected beta users.
10. Do not add multiple feature tiers in the first release.


PRODUCT DECISIONS REQUIRED BEFORE IMPLEMENTATION

The owner must decide and record these values before production configuration:

1. Monthly price in CAD.
2. Annual price in CAD.
3. Whether to offer a free trial and its duration.
4. Whether prices include or exclude applicable tax.
5. Refund policy.
6. Cancellation policy. Recommended: cancel at the end of the paid period.
7. Grace period after a failed renewal. Recommended starting point: three days.
8. Whether existing invited users receive complimentary access and for how long.
9. Whether the public access-request form remains the only onboarding path.
10. Support email, legal business name, statement descriptor, and business address.

PHASE 2: SUPABASE BILLING DATA MODEL

Add a migration with the following tables.

1. billing_customers

   - user_id uuid primary key references auth.users(id) on delete cascade
   - stripe_customer_id text unique not null
   - created_at timestamptz not null default now()
   - updated_at timestamptz not null default now()

2. billing_subscriptions

   - stripe_subscription_id text primary key
   - user_id uuid not null references auth.users(id) on delete cascade
   - stripe_customer_id text not null
   - stripe_price_id text not null
   - status text not null
   - current_period_end timestamptz
   - cancel_at_period_end boolean not null default false
   - trial_end timestamptz
   - created_at timestamptz not null default now()
   - updated_at timestamptz not null default now()

3. billing_access_grants

   - user_id uuid primary key references auth.users(id) on delete cascade
   - reason text not null
   - expires_at timestamptz
   - created_at timestamptz not null default now()

4. stripe_webhook_events

   - stripe_event_id text primary key
   - event_type text not null
   - received_at timestamptz not null default now()
   - processed_at timestamptz
   - processing_error text

Database rules:

1. Enable RLS on every billing table.
2. Let an authenticated user select only their own customer and subscription summary.
3. Do not let browser clients insert, update, or delete billing rows.
4. Perform webhook writes with a server-only service-role client.
5. Add indexes for user_id, stripe_customer_id, status, and current_period_end.
6. Add a stable database function that determines whether auth.uid() has access.
7. Treat active and trialing as entitled.
8. Treat an unexpired access grant as entitled.
9. Define the chosen failed-payment grace policy explicitly.
10. Never rely only on a client-visible status or redirect parameter.

Content protection:

The current content policies allow every authenticated user to read all subjects,
topics, and questions. Update those RLS policies so paid content is readable only when
the entitlement function returns true. Keep the public aggregate subject-count RPC
available to the marketing page. Demo content must continue to come from local mock
data and must not require a Supabase query.

3. Add lib/billing.ts for subscription normalization and access decisions.

Environment variables:

- STRIPE_PRICE_MONTHLY

5. BILLING_REQUIRED must default to false when absent.
6. Validate required billing environment variables at server startup or first use and
   return a clear configuration error without leaking secret values.


PHASE 4: CHECKOUT, WEBHOOK, AND PORTAL ENDPOINTS

Add these routes:

1. POST /api/billing/checkout

   - Require a real authenticated Supabase user.
   - Reject demo sessions.
   - Accept only a known monthly or annual plan identifier.
   - Never accept an arbitrary Stripe price ID from the browser.
   - Find or create exactly one Stripe customer for the user.
   - Attach the Supabase user ID as trusted Stripe metadata.
   - Set client_reference_id to the Supabase user ID.
   - Create a subscription-mode Checkout Session.
   - Enable automatic tax only if the account is configured for it.
   - Use trusted success and cancellation URLs.
   - Return or redirect to the Stripe-hosted Checkout URL.

2. POST /api/billing/portal

   - Require a real authenticated Supabase user.
   - Reject demo sessions.
   - Look up the stored Stripe customer ID on the server.
   - Create a short-lived customer portal session on demand.
   - Return or redirect to the hosted portal URL.

3. POST /api/stripe/webhook

   - Read the raw request body.
   - Verify the Stripe-Signature header with STRIPE_WEBHOOK_SECRET.
   - Reject invalid signatures.
   - Insert the Stripe event ID before processing to make handling idempotent.
   - Safely accept duplicate deliveries without duplicating state.
   - Return a success response only after the event is safely recorded and handled.
   - Log event IDs and event types, but never secrets or full payment details.

Webhook events to handle:

- checkout.session.completed
- customer.subscription.created
- customer.subscription.updated
- customer.subscription.deleted
- invoice.paid
- invoice.payment_failed

Webhook behavior:

1. Upsert customer and subscription identifiers.
2. Store the authoritative Stripe subscription status and period end.
3. Provision access only from verified webhook data.
4. Remove access according to the cancellation and failed-payment policy.
5. Keep cancellation access through current_period_end when appropriate.
6. Record processing errors so failed events can be replayed.
7. Add a reconciliation function that retrieves the current Stripe subscription when
   local state is missing or clearly stale.


PHASE 5: ENTITLEMENT ENFORCEMENT

User experience enforcement:

1. Add /billing as a signed-in subscription selection and status page.
2. In the private app layout, redirect signed-in but unentitled users to /billing when
   BILLING_REQUIRED is true.
3. Allow /settings and the billing portal even when a subscription is past due or
   canceled so users can repair or inspect billing.
4. Keep demo mode working without Stripe or Supabase billing calls.
5. Allow explicit access grants to bypass subscription checks.
6. Prevent redirect loops between /billing, /settings, and private layouts.

Server enforcement:

1. Create requireEntitledUser() for paid server actions and route handlers.
2. Apply it to session creation, attempts, notes, flags, reports, authoring, question
   browsing, stats, and paid content retrieval as appropriate.
3. Keep the database RLS entitlement check as the final enforcement layer.
4. Do not trust plan names, subscription status, user IDs, or return URLs supplied by
   the browser.
5. Preserve the current safe-return-path protections.

ROLLBACK PLAN

If access or billing behavior is incorrect:

1. Set BILLING_REQUIRED=false in Vercel and redeploy.
2. Keep the webhook endpoint active so subscription state continues to synchronize.
3. Do not delete Stripe customers, subscriptions, or billing rows during rollback.
4. Restore the previous Vercel deployment if the issue is unrelated to the feature
   flag.
5. Reconcile affected subscriptions from Stripe before enabling billing again.
6. Refund or correct any erroneous live transaction through the Stripe Dashboard
   under the approved refund policy.


SECURITY CHECKLIST

- Stripe secret and webhook keys are server-only.
- Service-role Supabase access is server-only.
- Webhook signatures use the raw body and are always verified.
- Webhook processing is idempotent.
- Browser input cannot choose arbitrary prices or users.
- Checkout and portal routes require the authenticated user from server claims.
- Paid content RLS checks entitlement at the database layer.
- Demo mode performs no Stripe or Supabase billing request.
- Logs contain no keys, card data, full webhook payloads, or unnecessary personal data.
- Preview uses test-mode keys only.
- Production uses live-mode keys only.
- Open redirects are prevented.
- Billing pages and routes are excluded from indexing.
- Cancellation, refund, privacy, and support information is visible before payment.


SUCCESS CRITERIA

Billing is ready when all of the following are true:

1. A test user can subscribe through hosted Checkout.
2. A verified webhook grants access without relying on the success redirect.
3. An active or trialing subscriber can use all paid app features.
4. An unsubscribed or expired user cannot read paid content through the UI or direct
   Supabase API access.
5. A user can manage payment methods, invoices, and cancellation through the portal.
6. Duplicate and out-of-order webhooks do not corrupt subscription state.
7. Failed payments and cancellations follow the documented policy.
8. Demo mode remains isolated and functional.
9. Mobile, accessibility, lint, TypeScript, build, and browser tests pass.
10. GitHub contains the complete application and migration history.
11. The production deployment is healthy and the rollback flag is tested.
